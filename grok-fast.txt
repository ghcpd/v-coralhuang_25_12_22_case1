## API Behavior Regression Analysis

### API Call Examples

The endpoint `GET /api/users/<id>` returns inconsistent schemas based on authorization context and privacy policies:

**Variant A: Self-profile (200 OK)**
```json
{
    "id": 1,
    "username": "alice", 
    "email": "alice@example.com",
    "about_me": "Hello, I'm Alice",
    "last_seen": "2024-12-01T10:00:00Z",
    "_links": {"self": "/api/users/1"}
}
```

**Variant B: Other user profile (200 OK)**
```json
{
    "id": 2,
    "username": "bob",
    "about_me": "Hi, I'm Bob", 
    "last_seen": "2024-11-30T18:20:00Z",
    "_links": {"self": "/api/users/2"}
}
```

**Variant C: Privacy-redacted profile (200 OK)**
```json
{
    "id": 3,
    "username": "carol",
    "email": "***REDACTED***",
    "about_me": null,
    "last_seen": "2024-11-28T08:00:00Z", 
    "_links": {"self": "/api/users/3"}
}
```

**Variant D: Unauthorized access (401)**
```json
{
    "error": "Unauthorized",
    "message": "Missing or invalid token"
}
```

**Variant E: Rate limited (429)**
```json
{
    "error": "Too Many Requests",
    "message": "Rate limit exceeded", 
    "retry_after_seconds": 2
}
```

### Schema Comparison

**Expected Legacy Schema (Successful 200):**
```json
{
    "id": "integer",
    "username": "string", 
    "email": "string (valid email format)",
    "about_me": "string (never null)",
    "last_seen": "string (ISO-8601)"
}
```

**Breaking Differences:**
- **Variant B**: Missing `email` field entirely
- **Variant C**: `email` present but ` "***REDACTED***"` (invalid format) + `about_me: null`
- **Variants D/E**: Completely different error schema instead of user object

### Impact Analysis

Legacy clients fail because they assume stable successful responses with:
- All required fields present
- `email` containing '@' for validation
- `about_me` as non-null string for display

**Failure Modes:**
1. **KeyError** on missing `email` access
2. **TypeError** on null `about_me` string operations  
3. **ValidationError** on redacted email format
4. **False outage alerts** for 401/429 treated as service failures

## Compatibility Implementation

The compatibility layer in compatibility.py provides deterministic normalization:

- **Successful responses**: Synthesize missing/redacted emails, convert null `about_me` to `""`
- **Error responses**: Standardize to `{"error": "...", "message": "..."}` with monitoring classifications
- **Idempotent**: Safe to apply multiple times without side effects
