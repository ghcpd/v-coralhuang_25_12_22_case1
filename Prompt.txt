## API Change

This is an **API schema instability regression**.

The endpoint:

* `GET /api/users/<id>`

returns **different response schemas for the same endpoint and method**, depending on request context.

### Observed Variants

The same endpoint may return:

1. **200 OK** user object with `email` present (own profile)
2. **200 OK** user object with `email` missing
3. **200 OK** user object with `email="***REDACTED***"`
4. **401** JSON error body (missing/invalid token)
5. **429** JSON error body with retry information

There is **no versioning or explicit indicator** of these differences.

---

## Legacy Client Assumptions (Immutable)

Legacy clients assume:

* Stable schema for successful responses
* `email` always exists and is a valid email
* `about_me` is always a string
* Any non-200 from this endpoint is treated as an outage

These assumptions are now broken.

## Required Compatibility Rules

### For 200 responses

* Missing or redacted `email` → synthesize `<username>@unknown.local`
* `about_me == null` → `""`
* Always output:

  * `id, username, email, about_me, last_seen`

### For non-200 responses

Normalize to:

```json
{ "error": "<short>", "message": "<detail>" }
```

Classification:

* 401 → `CLIENT_ERROR`
* 429 → `TRANSIENT`
* 5xx → `OUTAGE`
* 2xx → `OK`

All transformations must be **idempotent**.
